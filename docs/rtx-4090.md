# Horizon RTX: the one-machine build (ray tracing for VR at 90 Hz)

**Taking over?** [rtx-4090-handoff.md](rtx-4090-handoff.md): what is done, what is untested on the GPU, the open
questions and the next steps in order.

**Decision (4 November 2026).** This branch diverges from Horizon's main on purpose: it targets one machine (Windows
11, an RTX 4090, GeForce 621.01 or later, Vulkan) and drops the portability rules of [raytracing.md](raytracing.md)
("wgpu and Vulkan, no CUDA, no NVIDIA DLL at run time", Metal, the GL fallback) wherever they cost frame time. What
turns out better than main's path is ported back later, as a feature or a setting; nothing here is a candidate for
main as it stands.

**The target.** The state of the art of real-time path tracing (RTX Remix's techniques, [raytracing.md](raytracing.md)
"Next: the state of the art") at a cost that holds **90 Hz in VR: 11.1 ms of GPU for both eyes at KRVR's 1648x1328
an eye**, 2560x2048 an eye as the stretch goal, the desktop at 3440x1440 above 60 fps, and **a CPU frame under
11 ms at the 99th percentile while flying**, which the GPU budget is worth nothing without.

## Where it starts (measured 4 November 2026, 934b65a98, 3440x1440, 1024 chunks, RT lighting on)

| Case | GPU a frame | Of it, BLAS/TLAS | CPU frame p99 | Frames a second (worst 1 %) |
|---|---|---|---|---|
| Standing still | 10.4 ms | 0.15 ms | 14 ms | 90 (53) |
| Fast flight, 100 blocks/s | 9.3 ms | 0.14 ms | 38 ms | 43 (22) |
| Placing and breaking blocks in bursts (240 commands looped) | 13.6 ms | 0.35 ms | | 21 (11) |

The GPU is as steady in flight as at rest (p99 12.1 against 12.2 ms). The stutter is the CPU: chunk loading and
remeshing, and what the RT lighting does on the main thread with each section that comes, goes or changes.
In the headset (fake runtime, 1648x1328 an eye) the eyes took 8.1 to 9.6 ms after the levers of
[raytracing.md](raytracing.md) "GPU budget for Vision Pro"; the desktop trace kernel is 10 ms of 15.8, 70 % of it
ReSTIR GI.

**What the DirectX news is worth here.** Microsoft's DXR preview of 28 October 2026 (Clustered Geometry, Partitioned
TLAS, GPU-driven builds, Agility SDK 1.722-preview; NVIDIA's RTX Mega Geometry made standard) speeds up acceleration
structure *builds*. Horizon's cost 0.12 to 0.35 ms a frame even in the burst case, so it is the last lever, not the
first; its Vulkan form (`VK_NV_cluster_acceleration_structure`, `VK_NV_partitioned_acceleration_structure`) is in the
driver when wanted. DXR 1.2's opacity micromaps and shader execution reordering touch the trace kernel itself, and
those are in the plan.

## Phase 3, first brick: the top-level structure's instances written by the GPU

Why first: the structure is built every frame the hand or an entity moves (that is, always), and with wgpu's API its
7000 section instances go through the CPU each time (`hw_rays.rs` `finish`: `TlasInstance` rows, then wgpu-core's
per-instance resolution, encoding and tracking, then the submission's validation of every dependency for every pass
that binds it). Trimmed in the vendored wgpu (one allocation a frame instead of one an instance, one validation a
submission instead of one a pass), the rest only goes away by building the structure outside wgpu's API. What wgpu
30.0.1 and the vendored `wgpu-hal` give, checked:

- `Tlas::as_hal::<Vulkan>()` and `Blas::as_hal` reach the hal structures; the backported `raw_handle()` and
  `raw_buffer()` (`third_party/wgpu-hal/src/vulkan/mod.rs`) give their `VkAccelerationStructureKHR`, so
  `vkGetAccelerationStructureDeviceAddressKHR` gives each section's address once, when its structure is built (8
  bytes written to a GPU table at that moment, nothing a frame).
- A buffer made with `BufferUsages::STORAGE | TLAS_INPUT` (both public) is a storage buffer a compute pass writes
  and a valid instance input (`ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY_KHR` with a device address, `conv.rs`
  `map_buffer_usage`). The compute pass writes the `VkAccelerationStructureInstanceKHR` rows from the resident
  sections' table (address, origin, custom data) and the few moving instances' transforms from a uniform.
- `CommandEncoder::as_hal_mut::<Vulkan>()` records the build itself (`vkCmdBuildAccelerationStructuresKHR` into
  wgpu's own structure, a scratch buffer of hal's `ACCELERATION_STRUCTURE_SCRATCH` use, the barriers by hand:
  storage writes to build input, build to the trace kernel's reads), and
  `CommandEncoder::mark_acceleration_structures_built(&[], &[&tlas])` (in wgpu 30.0.1) tells wgpu it is built,
  with no dependency list to walk: the submission's validation costs nothing.
- The section structures stay wgpu's (`create_blas`, 64 builds a frame, nearest first): what changes is only who
  writes the instances and who records the top-level build.

The code goes in a crate of its own that may use `unsafe` (as `horizon-hdr` does, with `ash`), behind the `rtx`
feature; without it `hw_rays.rs` keeps today's path. Validation layers on for its first runs.

**Rules of the build.**

- Everything specialised sits behind the `rtx` feature or an option off by default, so the branch keeps building
  and running as main does without it, and a diff against main stays readable for the port back.
- Every phase is one measurement before and after on the same scenes: `HORIZON_SPIKES=20` with `horizon-ctl fly`
  for the CPU, `HORIZON_GPU_PASSES=1` and `tools/gpu_passes_report.py` for the GPU stages, `tools/vr_fake_run.py` for
  the eyes, the copy of NVIDIA's RTX Demo world and the RT test scene (`tools/rt_test_scene.sh`). Numbers go in this
  file's table, with the commit.
- The WGSL kernel stays as the fallback until the island renders the same picture (the captures compared), then it
  is frozen, not maintained twice.
