# Custom string component transport

This original Horizon extension carries bounded nonreserved namespaced string component patches through the existing vanilla `minecraft:custom_data` component, numeric ID 0. It adds no packet, channel, component registry ID or NBT serializer. It is source only and has not been built or run.

The pinned local transport paths share `lan::guest::stack_to_network` between server inventory output and the remote client's creative output. `item_sync` decodes both server snapshots and creative input. `horizon-protocol` already reads and writes `CUSTOM_DATA` as `Component::Nbt` with `horizon_world::nbt`. Previously the outbound stack builder omitted `StackData.other`, including custom data.

A v1 envelope uses the reserved compound key `horizon:string_components` inside custom data. Its fields are `version:1`, `original_present:0|1`, `patches` as a compound of scalar strings and `removed` as a list of component keys. At most sixteen combined keys, 128 UTF-8 bytes per key, 256 per value and 8192 encoded envelope bytes are allowed. Names use ordinary resource-location characters and exclude the reserved `minecraft` and `horizon` namespaces. Invalid UTF-16, unsupported value types, duplicate keys, conflicting patches, malformed removals, reserved-key collisions and unsupported envelope versions are errors.

Only actual `StackData.other` entries travel. An explicit `!namespace:key` with an empty compound is a persistent removal marker. A missing entry never implies removal and prototype values are not materialized by the transport. The separate effective inventory reader applies these patches over authoritative item prototypes. Strings must be losslessly convertible to UTF-8. The size check uses the existing bounded NBT writer.

An existing custom-data compound is cloned without altering unrelated NBT. Valid decoding removes only the envelope and restores the original component's presence, including an originally empty compound. A stack originally without custom data regains that absence. Unexpected content paired with an absent-original marker is rejected. Non-compound custom data cannot be merged with string patches. With no custom patches or removals there is no envelope; actual custom data passes through unchanged. Stacks without either retain their ordinary serialization.

Creative input must pass the existing permission, slot and count rules and reject malformed envelopes before any slot mutation. Normal inventory movement remains server authoritative. This envelope does not authorize client inventory patches, change survival click authority or expose a component mutator. Server snapshots and client actions must reject an entire failed update without converting errors into empty stacks, advancing synchronization caches or dropping nested bundle/crossbow children. Client predictions must be validated before their detached menu is committed.

The source path is connected through checked `Hub.stack`/`Hub.stacks`, shared stack encoding/decoding, inventory and container snapshots, merchant offers, equipment and entity candidates, remote creative actions and remote click batches. A malformed incoming client snapshot is rejected before mirror or state-ID changes. Creative ingress rejects before slot writes under existing permission checks. Nested errors reject their containing stack. Rejected outgoing snapshots leave their sent state unchanged. Entity candidates replace the previous snapshot only after complete construction; failed candidates skip entity tracking. Detached menu candidates and actual intermediate click packets are validated before any slot copy, merchant synchronization, drops or sounds. A failed candidate is discarded, and throw/drop paths validate before decrementing. No new survival inventory patch authority is added.

The original Option-returning stack helpers remain compatibility adapters for existing non-routing callers; active network paths use the checked functions. Prototype defaults are not sent as invented patches. Vanilla custom-data removal and arbitrary non-string custom component transport are outside this envelope format. Unsupported custom scalar types fail explicitly rather than being silently discarded. As before, the existing packet/NBT codec supplies outer stack limits; the 8 KiB bound applies to this envelope, not to unrelated original custom data.

These are original source changes, not runtime acceptance. No builds, checks, probes, tests, network sessions or games were run. Integrated and TCP craft/move/split/use behavior, vanilla interoperability and the native component reader still require later authorized validation. Source readiness is not evidence of successful TCP physical capture, audibility, rendering or consumption. Physical capture enablement remains a separate gameplay decision after this source handoff.
